## Accounted advisory investigation and owner review — 2026-11-11

The scientific driver now checkpoints evaluation, data-only Groq investigation, report, PDF and finish separately. `ScientificInvestigationStage` verifies published conservation provenance before advancing to investigating, freezes one operation/request/config/evidence identity, then uses the existing model admission, attempt/quota reservation, one-shot dispatch and usage settlement. Only metadata is returned to Workflow checkpoints. Reconciled capacity is released while text awaits owner review.

Workspace exposes a bounded `investigation` snapshot containing the actual validated `MetricEvidence` records (at most three), not only evidence IDs. POST `investigation-review` accepts an owner decision to accept or omit the exact draft digest under a current revision fence and idempotency key. Acceptance reviews advisory text and never establishes physical facts or changes metrics/verdicts. The user explicitly resumes through `scientific-run` afterward. Pending review blocks immutable report/PDF publication. Accepted hypotheses/recommendations and their metric references enter the single structured report; omission remains an incomplete reason in both screen and PDF. Coverage remains limited and terminal status partial because the six unreleased scientific method families remain required.

## Explicit owner AI disclosure consent — 2026-11-11

The workspace publishes the configured Groq provider, model and endpoint, the three data scopes (`source_context`, `source_adapter`, `numeric_investigation`), notice version and configuration digest. An authenticated owner must explicitly accept or revoke this exact disclosure through POST `ai-disclosure`. Revocation blocks future dispatch; it cannot recall data already transmitted. The existing source scanner remains a separate content screen and is not owner consent.

A reserved manifest entry is not evidence that file bytes exist or passed inspection.

- `GET /audits/{auditId}/revisions/{revisionId}/questions`: unresolved questions/context. `POST /audits/{auditId}/revisions/{revisionId}/answers`: validate, create successor revision, resume necessary inspection/adaptation; return successor ID.
- `GET /audits/{auditId}/revisions/{revisionId}/plan`: eligibility/experiments/accuracy/exclusions. `POST /audits/{auditId}/revisions/{revisionId}/run`: execute exact current plan after reservations. No approval for each individual check.
- `POST /audits/{auditId}/revisions/{revisionId}/cancel`: durable cancellation, stop dispatch, terminate live sandboxes; repeat safely.
- `GET /audits/{auditId}/revisions/{revisionId}/report`: structured report. `GET /audits/{auditId}/revisions/{revisionId}/report.pdf`: private PDF or explicit not-ready/expired response.
- `GET /audits/{auditId}/artifacts/{artifactId}`: authorize and stream available artifact, never expose bucket credentials/public URLs.
- `DELETE /audits/{auditId}`: immediate access tombstone, cancellation, idempotent physical cleanup.

Error envelope: `{error:{code,message,requestId,retryable,details?}}`; details bounded/redacted. Use 401 invalid credentials, 403 uninvited, 404 missing/other-owner resources, 409 stale revision/state/idempotency mismatch, 413 size, 422 invalid input, 429 rate/admission/capacity/budget, 503 provider unavailable. Stable `budget_exhausted` details explain financial limits without scientific judgment. Scientific unsupported is a readiness result.

Firestore listeners expose owner-visible summaries/events, never privileged ledgers. Reconnecting reads state; it does not dispatch work. Interface contracts are versioned independently of final styling.

The progress persistence helper now validates current ownership/revision fencing, compatible activity/stage/status, monotonic fixed-plan experiment counts, and Product event/coalescing limits. Its messages come from a fixed activity vocabulary, not raw model or sandbox output. Ordinary calls write progress metadata only. An internal caller may supply a validated lifecycle event to commit the state transition and matching progress together; neither path claims scientific success. Workflow integration, authenticated listener rules and result-derived counts remain required before this becomes end-to-end progress reporting.

## Contracts

`MetricEvidence` is a versioned internal scientific-output boundary with check/version and input/context/adapter/plan digests, experiment references, an absolute metric/unit, supported target/uncertainty, conservative interval, verdict/reason and limitations. It rejects contradictory passes, understated intervals, unit mismatches, missing supporting references and duplicate experiments. Missing target/bound is explicitly inconclusive. This structure does not authorize publication: a future trusted evidence service must resolve every reference, check released registry versions and confirm exact plan/revision provenance. It is not an AI output schema, and its JSON Schema export cannot express every runtime refinement. Python decision-to-wire parity exists; authoritative evidence publication and automatic report assembly remain pending.

The internal Python evidence module now separates diagnostic measurement from a conditional decision. It computes absolute scalar/vector drift without near-zero normalization and accepts an explicit target plus absolute uncertainty bound for interval-based classification. Missing targets/bounds, overlapping intervals and unrepresentable intervals remain inconclusive. The module does not infer units, establish the bound, validate provenance or enable checks. Those responsibilities remain with reviewed check implementations and the future evidence-report boundary; zero uncertainty must never be supplied as a convenient fallback.

Clarification routes now support GET of a saved `QuestionSet` and POST of `SubmitAnswers`. Private artifact GET is now locally implemented through an injected R2 read port. It reauthorizes after object retrieval and checks stored size/SHA-256 against immutable artifact metadata before streaming. The response is an octet-stream attachment with a generated filename and no-store headers; range requests are unsupported. A 30-second request/stream deadline, client cancellation and exact byte-count guard bound transfer. The R2 adapter cancels late bodies because the binding get API itself has no AbortSignal parameter. No source is rendered or executed. Historical artifacts remain downloadable until their original expiry; downloads need not belong to the newest revision. A stream already authorized cannot recall bytes delivered before a later deletion. Live R2/Worker behavior and dedicated report/PDF routes remain unverified.

`BaselineComparison` now represents the Python baseline comparator's bounded numerical result: exact numeric matched/mismatched status, compared-element count and one reason per declared observation. It does not mean the adapter is verified. The future adapter service must bind both runs to the same immutable inputs, runtime/image and baseline controls, require distinct fresh execution environments, validate extraction/mapping semantics and compare all required observations including time coordinates. The comparator never sorts, aligns, interpolates or relaxes tolerance. Signed zero compares numerically equal; non-finite, empty, wrong-dtype, unexpected and oversized inputs are rejected. At most 64 generated observation identifiers are accepted; total elements are capped by a server-supplied budget across both runs. This is a serialization/comparison limit, not a change to Product simulation cell/body limits. No public endpoint accepts a client comparison as trusted evidence.

The Python heat module now measures energy changes from explicit SI material/volume weights and balance residuals from independently extracted total source/outward powers. Mapping validation, thickness, unit conversion and quadrature uncertainty remain required before these diagnostics can support released checks. Testing records the derivation and counterexample showing why a residual alone is insufficient evidence of a bug.

The Python orbital module now exposes separate SI diagnostic routines for isolated positive-mass systems and fixed-central test trajectories. The first returns total energy, angular/linear momentum and center of mass; the second returns specific energy/angular momentum only. These functions measure supplied states, do not integrate or repair simulations, and do not issue verdicts. All scientific registry entries remain disabled pending the complete release gate. Testing records the derivations, observed fixture results and missing unit/frame/provenance/accuracy integration.

`EligibilityInput` and `EligibilityAssessment` now define a local deterministic prerequisite layer, bound to input/context/adapter digests and explicit domain. Assertions carry requirement IDs, satisfied/violated/unknown/conflicting states and evidence references. Resolved states require references, but schema validation does not verify reference ownership or truth: the future trusted context resolver must establish that before calling this internal helper. Missing/conflicting facts yield unresolved applicability; confirmed violations yield ineligible applicability, with all reasons retained. `applicability` is distinct from final selection `status`: the initial ten registry outlines were unreleased; four now have the explicitly scoped release described in the current integration status. This is not yet an executable CheckPlan, an endpoint, or dispatch authorization.

Requirement semantics follow Testing's planned families. `complete_gravity_model` means all mutually interacting bodies for an isolated system, or the single test trajectory and central parameter for a fixed-central profile; it does not require evolving the central body. `isolated_mutual_gravity` is separately mandatory for total momentum. `thermal_weights` covers declared layout, physical material factors and quadrature/volume convention. Explicitly confirmed zero source or zero boundary flux can satisfy their observation requirements without inventing measured data. The outline predicates do not replace future profile-specific numeric/shape/unit validation or complete method specifications.

The local Python numeric boundary accepts bounded NPY v1/v2 real numeric arrays and UTF-8 CSV with explicitly declared header presence.
