# Siphon database and artifact storage

## Investigation stage and review records — 2026-11-11

`scientificInvestigationStages/{revisionId}` freezes owner/audit/revision/input, source and investigation generations, evaluation/AI operation IDs, evidence/request/configuration digests and native creation time. Existing `investigationTasks`, `modelJobs`, sanitized `modelReceipts` and revision `investigationDrafts/{operationId}` bind the settled draft to deterministic metric IDs. Raw provider bodies and credentials are absent. Drafts remain `awaiting_review`; immutable owner decisions live separately at revision `investigationReviews/current`, with exact operation/draft/evidence identity, accepted/omitted status and native review time. Server-only `requests` receipts fence POST replay and reject key reuse with different input. Deletion/retention must include these new records; a scheduler sweep is still unverified.

Workspace returns only the shared advisory snapshot, including provider/model, IDs/digests, bounded hypothesis/recommendation text, review state and expiry. It rechecks draft hashes, owned evidence and settled provider usage; expired text is labelled expired and cannot be accepted. The report assembler rechecks the same proof, refuses pending review and catalogs accepted advisory provenance separately from numerical evidence. A report never becomes full coverage because its owner accepted text.

Owner AI consent is stored at `audits/{auditId}/revisions/{revisionId}/aiDisclosure/current`, with owner/audit/revision/input identity, configuration digest, accepted/revoked decision and timestamps. The disclosure digest covers the visible provider/model/endpoint, fixed scope list and notice version, never the API key. POST idempotency receipts live under server-only `requests`. Workspace reports `required` if the current input or provider configuration no longer matches the saved decision. Dispatch reads the consent record in its authorization transaction; raw source/model payloads are not added to consent records or checkpoints.

## Scientific completion receipt — 2026-11-11

`scientificFinishStages/{revisionId}` is server-only immutable completion metadata. It records the owner, original audit/revision/input/generation fence, PDF operation, report ID/digest, PDF hash, partial status and native finish timestamp. The receipt commits atomically with terminal progress, after matching report/PDF/termination proof and reconciled capacity release. A lost Workflow checkpoint may replay only the same operation and fence against its exact terminal successor; current invitation, owner, nondeleted audit and current revision remain mandatory. Replay performs no provider call, capacity release or new progress write. A missing receipt never authorizes reconstruction from terminal status alone. No populated receipt or hosted completion is established by the implementation.

## Ownership and persistence choices

[Product requirements](PRODUCT_REQUIREMENTS.md) owns scope/limits; [Architecture](ARCHITECTURE.md) owns state enums/contracts/API; [Security](SECURITY.md) owns authorization; [Testing](TESTING.md) owns validation. This document owns persisted entities, indexes, transactions, retention, and deletion. Keep them synchronized.

Use Firestore Standard for bounded structured records, Firebase Authentication for identity, private R2 Standard for bytes. No SQL, Firebase Storage, or inline large arrays. All records carry `schemaVersion`, creation/update server timestamps, and an ownership relationship where relevant. Store timestamps natively in Firestore; RFC 3339 UTC on API boundaries.

Money uses integer micro-USD (1 USD = 1,000,000 micro-USD), never binary floating-point balances. Byte sizes are nonnegative integers; calculate units explicitly. Provider monthly-operation accounting follows the verified provider billing period; user/global daily admission uses UTC dates. Provider prices are effective-dated and versioned; preserve usage categories/rate versions for later reconciliation. Finite scientific metrics are numbers with unit/scale metadata; non-finite outcomes become explicit invalid-data records, not JSON NaN.

## Collections

- `users/{uid}`: minimal display name, created/last-seen time. UID comes from verified Firebase identity, never a body field. Do not store provider tokens/passwords.
- `testers/{uid}`: active flag and invitation provenance; server/admin writable only. Bootstrap approved UIDs out of band. An administrator is not a public API role in v1.
- `audits/{auditId}`: ownerUid, title, domain, currentRevisionId, created/updated, deletionRequestedAt. Clients cannot change ownership/domain through direct writes.
- `audits/{auditId}/revisions/{revisionId}`: parentRevisionId, ownerUid, source manifest/hash, answer/context hashes, bounded context, canonical stage/status/readiness, effective policy, plan digest/ref, current operation/lease reference, cancellation time, bounded progress summary, report references, scientific/software versions. Input snapshots freeze on first cost-incurring admission. Outcome fields evolve through fenced transitions.
- Revision subcollections `questions`, `answers`, `plans`, `experiments`, `evidence`, `events`, `reports`: versioned, bounded records corresponding to Architecture contracts. Plans/results/reports are append-only published versions; a current pointer may advance without rewriting old evidence. Unbounded explanation text goes to an artifact.
- `audits/{auditId}/artifacts/{artifactId}`: owner, kind, safe display path, private object key, SHA-256, MIME, byte size, retention class, references, created/expires time, lifecycle (`reserved`, `ready`, `expired`, `deleting`, `deleted`, `failed`). An artifact can be shared by revisions of the same audit; never deduplicate across owners. Freeze bytes after ready.
- Server-only `operations/{operationId}`: revision/stage, request digest/idempotency key hash, attempt, fencing token, provider request/job/sandbox handles, reservation references, dispatch/outcome (`reserved`, `dispatching`, `succeeded`, `failed`, `unknown`), usage, heartbeat, timestamps. Do not expose credentials or full raw model responses here.
- Server-only `reservations/{reservationId}`: provider/resource, audit/revision/operation, reserved amount, measured usage, disposition, accounting period, reconciliation state. Unknown completion remains reserved. Release/refund is a separate idempotent transition, not deletion of history.
- Server-only `budgets/{scopeId}`, `dailyQuotas/{scopeAndUtcDate}`, `rateWindows/{scopeAndWindow}`, `slots/{scopeId}`: atomic counters/leases supporting Product LIM policies. Keep global and user scopes separate. No client editing.
- Server-only `configuration/{version}` and `maintenance/{jobId}`: effective policies/check-registry digest references and bounded reconciliation/deletion cursors. Code remains the reviewed scientific-registry source; database configuration cannot inject executable physics checks.

Each event has sequence, stage, timestamp, kind, concise message, optional check/experiment ID. Persist bounded summaries, not token streams or unbounded stdout. Follow LIM-12 and retain terminal summary even when append capacity is exhausted.

Implemented progress records use revision.progress as the bounded current summary, with schemaVersion, auditId/revisionId, stage/status, fixed activity/message, native updatedAt, optional experiment counts, eventCount and timelineCapped. Timeline records at events/{zero-padded-sequence} carry the same summary plus sequence and kind (transition/activity). A transaction reads invitation, audit ownership/current pointer, revision generation/input digest and policy before writing. Ordinary updates coalesce within the policy interval; persisted stage/status changes bypass that interval. Once eventCount reaches the cap, only the current summary changes. Exact duplicates and repeated terminal updates do not append records. Ordinary progress updates do not advance the dispatch generation; an explicitly supplied lifecycle transition does. Browser rules are now authored as described below, but orchestration and deployed rules verification remain pending; producer code must derive counts from actual experiment results.

## R2 key structure and downloads

Content-write accounting (2026-10-28): `configuration/r2_class_a_period` supplies a verified counterKey, startsAt and endsAt for the provider billing period; `budgets/{counterKey}` limits Class A attempts. An uncertain outcome retains the storage reservation; reconciliation and orphan cleanup remain pending. Native expiry metadata is unchanged. No automatic retry or rollback of a possibly successful R2 write occurs.

Implemented upload reservations (2026-10-28): `budgets/r2_storage_bytes` tracks allocated bytes using the existing limit/reserved/spent/halted counter contract. ## Retention and deletion

Initial policy defaults (change deliberately and show to users): original uploads/raw numerical evidence/logs expire 7 days after creation; structured reports and generated report charts/PDFs expire 30 days; compact private audit/revision metadata remains until user deletion or the project's account-retention policy changes. Financial/security reconciliation records contain minimal identifiers and remain 90 days, with raw source/answers excluded. Retention does not promise full rerunnability after source expiry.

Deletion immediately tombstones audit, denies listeners/downloads, cancels execution, and queues bounded recursive cleanup. Remove subcollections explicitly: deleting a parent document is insufficient. Remove every R2 artifact even if shared by revisions. Reconcile unknown provider charges and terminate handles before final cleanup; keep only minimized financial records for their retention interval. Retry failed cleanup with a cursor and visible pending status. Expired objects must be denied even before physical removal.

Use daily scheduled sweeps and R2 lifecycle rules as secondary cleanup. Do not depend on Firestore TTL features requiring a billing upgrade; application deletion is authoritative. Abandoned reserved uploads are removed after 24 hours. Provider-side paused snapshots/volumes are not created in v1; kill rather than pause and confirm deletion behavior during integration.

## Schema evolution and release checks

Implementation detail (2026-10-28): server-only `requests/{ownerAndRouteAndKeyHash}` stores idempotency receipts for non-provider HTTP mutations. Fields are schemaVersion, ownerUid, auditId, createdAt, updatedAt, and either requestDigest for creation or a bounded command result for bodyless cancellation/deletion. Hash the owner/route/key tuple; do not store raw keys or duplicate private request bodies. A replay reauthorizes the invitation and owner. Creation/cancellation additionally require a non-deleted audit; deletion alone can replay against its owner's tombstone. Conflicting creation payloads return 409. Receipts are retained while their audit exists and removed during its recursive deletion; stale keys must never resurrect a deleted audit. These receipts are separate from financially reserved provider `operations`. Browser access is denied. Cleanup implementation remains pending.

Cancellation/deletion maintenance records use a deterministic hash of the command kind and audit/revision IDs, so repeated commands cannot reset cleanup. Fields are schemaVersion, id, kind (`cancel_revision` or `delete_audit`), auditId, ownerUid, revisionId, status, phase, cursor, attempts, createdAt, updatedAt, and nextAttemptAt. Initial status is pending and phase is terminate_and_reconcile. Recording a job is not termination evidence. Repeated same-key commands replay the original receipt; a new key may observe confirmed cleanup when a future worker has completed the job. A missing physically deleted audit returns 404 without recreating anything. Provider operations also store auditId, ownerUid and inputDigest alongside revisionId/fence for transactional authorization. Reconciliation must preserve those bindings without reopening access.

Version contracts at boundaries. Migrate through explicit bounded scripts/jobs with dry-run counts, backups of necessary metadata, and idempotent resumability. Never mutate historical raw evidence to fit a new schema; write new interpretations with provenance. Breaking changes require readers for existing retained versions or an explicit incompatibility message.
